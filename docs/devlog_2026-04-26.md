## 작업 1: DB 마이그레이션 — `chat_logs` 컬럼 추가 + `correction_notes` 테이블 신규 생성

### **[주요 작업 내역]**

---

### **[상세 작업 내용]**

- **작업 내용:**
  - Alembic 마이그레이션 파일(`b2c3d4e5f6a7`)을 새로 작성했습니다.
  - `chat_logs`에는 AI API 호출 결과를 추적하기 위한 컬럼 4개를 추가했습니다.
  - `correction_notes`는 관리자가 "이 질문에 대해 이 답변이 맞다"는 정정 내역을 기록하는 테이블로 신규 생성했습니다.
  - 마이그레이션 이후 SQLAlchemy ORM 모델도 같이 수정해야 런타임에서 필드를 인식합니다. 이것을 놓치면 `AttributeError`가 발생하기 때문에 항상 마이그레이션 파일과 ORM 모델을 같이 수정합니다.

- **설계 의도 및 근거:**
  - **왜 `chat_logs`에 토큰 정보를 넣었나?** 원래 `chat_logs`의 `total_cost` 컬럼은 있었지만 항상 `NULL`이었습니다. 비용을 계산하려면 "어떤 모델을 몇 토큰 사용했는가"를 알아야 합니다. 토큰 수는 OpenAI API 응답의 `response.usage`에서 쉽게 꺼낼 수 있으므로 이것을 DB에 저장하는 것이 가장 정확한 집계 방법입니다.
  - **왜 `correction_notes`를 별도 테이블로?** 정정 노트는 특정 피드백(`chat_logs` 행)에 1:N으로 달리는 데이터입니다. `chat_logs` 컬럼으로 넣으면 정규화가 깨지고 관리자가 여러 버전의 정정 노트를 작성할 수 없습니다. 별도 테이블로 분리하고 `feedback_id`로 FK를 걸었습니다.

### **[특이사항 및 트러블슈팅]**

- **문제 및 고민:**
  - ORM 모델에 필드를 추가하면서 `Mapped[Optional[int]]`처럼 컬럼 타입 없이 쓰는 방식이 가능한지 헷갈렸습니다. SQLAlchemy 2.x에서는 Python 타입(`int`, `str`)으로부터 DB 컬럼 타입을 자동 추론하기 때문에 `mapped_column(nullable=True)`만으로도 `INTEGER NULL` 컬럼이 됩니다.

- **해결 및 결정:**
  - 마이그레이션 실행 결과 `Running upgrade a1b2c3d4e5f6 -> b2c3d4e5f6a7` 로그가 깔끔하게 찍히는 것을 확인하고 진행했습니다.

- **새롭게 배운 점:**
  - **마이그레이션과 ORM 모델은 항상 같이 수정한다.** DB 스키마를 바꿨는데 ORM 모델을 안 바꾸면 서버는 뜨지만, 해당 필드에 쓰거나 읽으려는 코드가 실행될 때 런타임 오류가 납니다. 두 파일을 같은 커밋에 묶는 것이 좋습니다.

## 작업 2: 유저 활성/비활성 토글 PATCH API 구현

### **[주요 작업 내역]**

- `PATCH /admin/users/{user_id}/active?is_active=true|false` 엔드포인트 신규 추가
- `AdminService.set_user_active` + `AuthService.set_user_active` 메서드 구현
- 토글 실행 시 감사 로그(`USER_ACTIVATE` / `USER_DEACTIVATE`) 자동 기록

---

### **[상세 작업 내용]**

- **작업 내용:**
  - 관리자 패널 유저 목록에서 "활성화/비활성화" 버튼을 눌렀을 때 실제 DB에 반영되는 API를 만들었습니다.
  - 기존에 `GET /admin/users`는 이미 있었지만, 개별 유저의 상태를 바꾸는 API는 없었습니다.
  - 도메인 설계 원칙상 `admin` 도메인이 `users` 테이블을 직접 건드리는 것은 금지되어 있어서, `AuthService.set_user_active`를 만들고 `AdminService`가 그것을 호출하는 방식을 사용했습니다.

- **설계 의도 및 근거:**
  - **왜 PATCH?** 유저 자원 전체를 교체(PUT)하는 게 아니라 `is_active` 하나만 바꾸는 부분 수정이므로 PATCH가 맞습니다.
  - **왜 body가 아닌 query parameter?** `is_active`는 `true`/`false` 단일 값이라 JSON body보다 query parameter가 훨씬 호출하기 편하고, Swagger UI에서도 체크박스로 표시됩니다.
  - **도메인 격리:** `admin` 서비스에서 `User` 모델을 직접 `UPDATE`하면 나중에 `auth` 도메인의 유저 비활성화 비즈니스 로직이 생겼을 때 중복 구현이 됩니다. `AuthService`에 메서드를 만들어 두고 `AdminService`가 위임하는 구조가 더 확장성이 좋습니다.

- **데이터 구조 변경:**

  ```python

      await self._auth_service.set_user_active(user_id=user_id, is_active=is_active)

### **[특이사항 및 트러블슈팅]**

- **문제 및 고민:**
  - `AuthService`가 `AdminService`와 같은 세션을 공유하기 때문에, `AuthService.set_user_active`에서 `commit()`을 호출하면 안 됩니다. `commit()`은 트랜잭션 경계를 관리하는 `AdminService`에서만 호출해야 합니다.
  - 만약 `AuthService` 안에서 `commit()`을 부르면, 나중에 `add_audit_log`가 같은 트랜잭션에 묶여야 할 감사 로그가 별개로 나뉘어버리는 문제가 생길 수 있습니다.

- **해결 및 결정:**
  - `AuthService.set_user_active`는 `execute(UPDATE)`만 하고 커밋을 하지 않습니다. 커밋은 모든 로직이 끝난 뒤 `AdminService`에서 한 번만 합니다. 이 패턴을 **"트랜잭션 경계는 서비스 최상위에서 닫는다"** 라고 이해했습니다.

- **새롭게 배운 점:**
  - 여러 서비스가 같은 세션을 공유할 때, `commit()`을 어디서 호출하느냐가 중요합니다. 호출 스택에서 가장 바깥쪽(오케스트레이터 역할을 하는 서비스)에서만 `commit()`을 호출하는 것이 원칙입니다. 안쪽 서비스가 중간에 `commit()`을 호출하면 트랜잭션이 조기에 끊어져 이후 작업이 별개 트랜잭션으로 처리됩니다.

## 작업 3: 감사 로그 스펙 확장 + ChatMonitor 페이지네이션

### **[주요 작업 내역]**

- `AuditLogItem` 스키마에 `audit_id`, `admin_name`, `ip_address`, `diff` 필드 추가
- `list_audit_logs` 서비스가 `Admin.login_id` JOIN + `page`/`size` 페이지네이션을 지원하도록 변경
- `ChatMonitorResponseData`에 `total_count`, `total_pages` 필드 추가
- `GET /admin/audit-logs`에 `page`, `size` query parameter 추가

---

### **[상세 작업 내용]**

- **작업 내용:**
  - 기존 감사 로그 API는 "누가(admin_id) 무엇을(action) 언제(created_at)" 만 반환했습니다. 하지만 관리자 화면에서는 `admin_id`(UUID)보다 관리자 이름이 필요하고, IP와 변경 diff도 같이 보여줘야 감사 로그로서 의미가 있습니다.
  - `AdminRepository`에 `list_audit_logs_page` 메서드를 새로 만들어서 `Admin` 테이블과 JOIN하고 페이지네이션을 지원하도록 했습니다.
  - 기존 `list_audit_logs` 메서드(limit만 받는 구 버전)는 레거시 호환을 위해 남겨두고, 새 메서드를 추가했습니다.

- **설계 의도 및 근거:**
  - **왜 서비스가 아닌 레포지토리에서 JOIN?** JOIN은 DB 쿼리 레벨에서 하는 것이 메모리 효율적입니다. 서비스에서 `admin_id`로 `Admin`을 따로 조회하면 N+1 쿼리 문제가 생깁니다.
  - **왜 `total_count`/`total_pages`를 ChatMonitor에 추가?** 프론트엔드가 페이지네이션 UI를 그리려면 전체 건수와 총 페이지 수를 알아야 합니다. 이 값 없이는 "다음 페이지" 버튼을 언제 비활성화할지 알 수 없습니다.

- **데이터 구조 변경:**

  # backend/src/app/domains/admin/repository.py — 페이지네이션 + JOIN 메서드 추가

  async def list_audit_logs_page(
      self, *, page: int = 1, size: int = 25
  ) -> tuple[Sequence[tuple[AdminAuditLog, str | None]], int]:
      offset = (page - 1) * size
      stmt = (
          select(AdminAuditLog, Admin.login_id)
          .outerjoin(Admin, Admin.id == AdminAuditLog.admin_id)
          .order_by(desc(AdminAuditLog.created_at))
          .offset(offset)
          .limit(size)
      )
      count_stmt = select(func.count()).select_from(AdminAuditLog)
      res = await self._session.execute(stmt)
      total = (await self._session.execute(count_stmt)).scalar() or 0
      return res.all(), total
  ```

### **[특이사항 및 트러블슈팅]**

- **문제 및 고민:**
  - `Admin` 테이블에는 `name` 컬럼이 없고 `login_id`만 있었습니다. 계획에는 `Admin.name`을 가져오도록 적혀 있었지만, 실제 모델을 보니 이름 컬럼이 없어서 `login_id`를 `admin_name` 필드에 매핑했습니다.

- **해결 및 결정:**
  - 없는 컬럼을 만들기보다 존재하는 `login_id`를 대신 사용하는 것이 현실적이었습니다. 어차피 감사 로그에서 "누가 했는가"를 파악하는 목적이라면 로그인 ID로도 충분합니다.

- **새롭게 배운 점:**
  - `outerjoin` vs `join`의 차이를 실감했습니다. `join`을 쓰면 `admin_id`가 `admins` 테이블에 없는 경우(예: 삭제된 관리자) 해당 감사 로그 행이 결과에서 통째로 사라집니다. `outerjoin`을 써야 "관리자는 없지만 감사 로그는 표시"가 됩니다. 감사 로그는 기록 보존이 목적이므로 무조건 `outerjoin`이 맞습니다.

## 작업 4: AI 비용·토큰 추적 — `monitoring_cost` 실제 집계 구현

### **[주요 작업 내역]**

- `_generate_rag_answer` 함수가 `(content, usage)` 튜플을 반환하도록 변경

## 작업 5: 레이턴시 차트 — `monitoring_latency` 시계열 집계 구현

### **[주요 작업 내역]**

- `monitoring_latency` 서비스 메서드를 빈 배열 반환에서 실제 p50/p95 시계열 집계로 교체
- `1h`=5분 버킷, `24h`=1시간 버킷, `7d`=1일 버킷으로 범위별 구분
- PostgreSQL `PERCENTILE_CONT` 윈도우 함수 사용

---

### **[상세 작업 내용]**

- **작업 내용:**
  - `range_value`("1h"/"24h"/"7d")에 따라 조회 기간과 버킷(집계 단위)을 다르게 적용했습니다.
  - PostgreSQL의 `PERCENTILE_CONT(0.5) WITHIN GROUP (ORDER BY response_time_ms)` 문법으로 p50(중앙값), `PERCENTILE_CONT(0.95)`로 p95를 계산합니다.
  - 1시간 범위일 때는 5분 단위로 더 세밀하게 보여줘야 해서 `floor(epoch / 300) * 300` 방식으로 버킷을 만들었습니다.

- **설계 의도 및 근거:**
  - **왜 p50과 p95 둘 다?** 평균(avg)은 일부 매우 느린 요청이 있으면 크게 왜곡됩니다. p50(중앙값)은 "일반적인 사용자 경험"을 나타내고, p95는 "상위 5%의 느린 요청이 어느 정도인가"를 나타냅니다. 레이턴시 모니터링의 표준 지표입니다.
  - **왜 `role = 'system'`으로 필터?** AI 응답 시간(`response_time_ms`)은 에이전트 노드 완료 시 `role='system'`으로 저장됩니다. `role='user'` 메시지는 응답 시간이 없으니 제외해야 합니다.

- **데이터 구조 변경:**

  ```python
  # backend/src/app/domains/admin/service.py — monitoring_latency 실제 구현

  async def monitoring_latency(self, *, range_value: str) -> dict[str, Any]:
      now = datetime.now(timezone.utc)

      # 범위별 기간 + 버킷 설정
      if range_value == "1h":
          since = now - timedelta(hours=1)
          # 5분(300초) 버킷
          bucket_expr = text(
              "to_timestamp(floor(extract(epoch from created_at) / 300) * 300)"
          ).label("ts")
      elif range_value == "24h":
          since = now - timedelta(hours=24)
          bucket_expr = func.date_trunc("hour", ChatLog.created_at).label("ts")
      else:  # 7d
          since = now - timedelta(days=7)
          bucket_expr = func.date_trunc("day", ChatLog.created_at).label("ts")

      stmt = (
          select(
              bucket_expr,
              func.percentile_cont(0.5).within_group(ChatLog.response_time_ms).label("p50"),
              func.percentile_cont(0.95).within_group(ChatLog.response_time_ms).label("p95"),
              func.count(ChatLog.id).label("cnt"),
          )
          .where(
              ChatLog.role == "system",
              ChatLog.response_time_ms.isnot(None),
              ChatLog.created_at >= since,
          )
          .group_by(literal_column("ts"))
          .order_by(literal_column("ts"))
      )

      rows = (await self._session.execute(stmt)).all()
      points = [
          {"ts": row.ts.isoformat(), "p50": int(row.p50), "p95": int(row.p95), "count": row.cnt}
          for row in rows
      ]
      return {"range": range_value, "points": points}
  ```

---

### **[특이사항 및 트러블슈팅]**

- **문제 및 고민:**
  - `PERCENTILE_CONT`는 PostgreSQL 전용 문법이라 SQLAlchemy ORM 표현식으로 깔끔하게 작성하는 방법을 찾아야 했습니다.
  - SQLAlchemy에서 `within_group()`을 지원하는 것을 확인하고 `func.percentile_cont(0.5).within_group(ChatLog.response_time_ms)` 형식으로 작성했습니다.

- **해결 및 결정:**
  - 1시간 범위의 5분 버킷은 SQLAlchemy ORM 표현식으로 표현하기 복잡해서 `sqlalchemy.text()`로 raw SQL을 적었습니다. 특정 DB 전용 함수는 ORM보다 raw SQL이 더 직관적이고 유지보수하기도 쉬운 경우가 있습니다.
  - `GROUP BY`에서 label 이름("ts")으로 집계해야 해서 `literal_column("ts")`를 사용했습니다.

- **새롭게 배운 점:**
  - `p50/p95` 지표가 왜 레이턴시 측정에서 표준인지 이해했습니다. 평균은 outlier에 취약하지만 백분위수는 전체 분포에서 특정 위치의 값을 정확하게 잡아줍니다.
  - SQLAlchemy에서 `func.percentile_cont().within_group()` 문법을 처음 써봤습니다. PostgreSQL 통계 함수를 ORM에서도 쓸 수 있다는 걸 배웠습니다.

## **[전체 회고]**

이번 작업에서 "있는 척하지 말고 실제로 동작하게 만든다"는 원칙을 실천했습니다.
stub 코드가 쌓이면 겉으로는 완성된 것처럼 보이지만 실제로는 아무 데이터도 없고, 나중에 "왜 비어있지?"를 디버깅하는 시간이 더 많이 걸립니다.

특히 이번 작업에서 가장 많이 배운 부분은 다음 세 가지입니다.

1. **트랜잭션 경계는 오케스트레이터에서 관리한다.** 여러 서비스가 같은 세션을 공유할 때, `commit()`은 가장 바깥쪽 서비스에서만 호출해야 합니다. 안쪽 서비스가 `commit()`을 중간에 호출하면 감사 로그가 비즈니스 로직과 다른 트랜잭션으로 나뉘어버립니다.

2. **JOIN은 DB에서, N+1은 금지.** 여러 테이블의 데이터가 필요하면 서비스 레이어에서 개별 조회를 반복하지 말고 레포지토리에서 JOIN으로 가져와야 합니다. 감사 로그 + 관리자 이름을 가져올 때 `outerjoin`을 사용해 N+1을 피했습니다.

3. **commit 후 DB 생성 값은 refresh로 동기화.** `session.add()` + `commit()` 후에 Python 객체에서 `server_default`로 생성된 값(id, created_at)을 쓰려면 반드시 `session.refresh()`를 호출해야 합니다.
